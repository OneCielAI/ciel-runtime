Auto-compact trigger: what the client actually computes, and why the pin is safe
Re-checked 2026-10-19 against commit 50e7906 (HEAD) and the live provider table.
No transcript, key, or message content is reproduced here; only numbers.

1. Client-side threshold (from the recorded build evidence, not documentation)

Source: docs/journal/2026/10/15/diagnostics/claude-autocompact/evidence/
05-claude-code-2.1.300-autocompact-source.txt (Claude Code 2.1.300 binary, plain-JS
region; minified names valid for that build only). Both environment names used by
this fix are present in the installed 2.1.292 binary as well:
  CLAUDE_AUTOCOMPACT_PCT_OVERRIDE      -> bin/claude.exe, claude-code-win32-x64/claude.exe
  CLAUDE_CODE_AUTO_COMPACT_WINDOW      -> same two files

The build computes:
  effective_window = window - min(model.maxOutputTokens, 20000)
  default_threshold = effective_window - 13000
  override_threshold = min(floor(effective_window * pct / 100), effective_window - 13000)

So the override percentage is applied to the window AFTER up to 20,000 output
tokens are deducted, and is additionally capped 13,000 below that. It is not a
percentage of the raw CLAUDE_CODE_AUTO_COMPACT_WINDOW value.

Regression, restated in the client's own terms: the client would have compacted
at 839,000 tokens while the router stopped forwarding unmodified requests at
716,750. The trigger sat 122,250 tokens above the trim point, so it could never
be reached. The measured token basis after the last boundary peaked at 817,921,
which is below 839,000 and above 716,750 - exactly the window in which the session
sent 1,582 requests, zero compaction requests, and grew without bound.

3. Version robustness

The pinned percent is derived from the raw window, so for any internal deduction
d of the client (d >= 0):
  floor((window - d) * pct / 100) <= floor(window * pct / 100) <= budget
The trigger therefore stays at or below the budget for every build that deducts
from the window at all, without encoding the 20,000 / 13,000 constants. Pinning
to the exact effective window (84 % here) would land at 715,680, 1,070 under the
budget, but would depend on constants observed in a single build. The conservative
pin is deliberate: an overshoot would silently restore the incident.

4. One trim point only

cap_anthropic_body -> budget.compact_anthropic(input_budget)
                   -> prompt_compaction.compact_anthropic_body_for_budget(budget_tokens)
The runtime guard and the environment now read the same guarded_input_budget()
helper, so there is no second, smaller threshold that the trigger could exceed.
A translated Codex checkpoint on the Anthropic wire is the only case that trims
with native_owns=False; it is a Codex launch and does not consume this env.

6. What this does not establish

No live Claude launch was made to read the emitted environment from a running
child in this re-check; the values come from the shipped code path plus the
saved configuration. The 20,000/13,000 deductions come from one inspected build
and are not documented; the pin does not depend on them, as shown in section 3.
