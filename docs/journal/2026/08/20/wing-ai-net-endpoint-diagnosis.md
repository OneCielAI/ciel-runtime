# Wing AI-Net endpoint diagnosis

## Observed command

- Wing ran unauthenticated HTTP GET requests against ports 3603, 3600, and
  3601 and labeled every thrown `Invoke-WebRequest` exception as `FAIL`.
- The shell is Windows PowerShell `5.1.20348.4294`.

## Direct evidence

- `GET http://100.94.212.25:3603/mcp` returned `401` with
  `missing Authorization: Bearer <agent_api_key>`.
- Wing has a 75-character `AINET_API_KEY`, and managed Codex configuration
  supplies it in the MCP Authorization header.
- An authenticated MCP `initialize` POST returned `200`, a 36-character MCP
  session header, and a 234-byte response.
- The configured authenticated notification SSE endpoint returned `200` and
  delivered 391 bytes during a three-second diagnostic window.
- `GET http://100.94.212.25:3600/api/v1/` returned `308` with location
  `/api/v1`; following it reached `/api/v1` and returned `404`.
- No recent AI-Net authentication failure was found in the inspected Ciel
  router logs.

## Conclusion

- Correction after recovering the complete Dave session transcript: Dave did
  include `Authorization = "Bearer $env:AINET_API_KEY"` in the MCP initialize
  calls preceding the unauthenticated three-URL probe. The earlier analysis was
  incomplete because it examined only the later probe output.
- The first authenticated initialize reached the MCP server and returned `406`
  because its `Accept` header was incomplete, not because authentication failed.
- The next initialize included the required MCP headers but omitted Windows
  PowerShell 5.1's `-UseBasicParsing`; it displayed `Security Warning: Script
  Execution Risk` and then raised the reported NullReference error.
- Repeating the same request with `-UseBasicParsing` returned `200`, issued an
  MCP session ID, and a subsequent `tools/list` returned the complete tool list.
- Keeping `Mcp-Protocol-Version` while adding `-UseBasicParsing` was separately
  reproduced and returned `200`, proving that header was not the failure cause.
- The later three-URL connectivity probe did omit authentication, so its two
  `401` responses remain expected but do not describe the preceding MCP calls.
- The `308` is a trailing-slash normalization response. The resulting
  `/api/v1` base path is not a valid resource and returns `404`.
- The Dave session ledger contains one function call for the failing command;
  the duplicated terminal rendering is not evidence of two executions.
- The evidence rules out a missing `AINET_API_KEY` in Dave's execution
  environment and identifies PowerShell response parsing as the immediate
  failure path.
- Later file-time verification showed that
  `%APPDATA%\\ciel-runtime\\codex-mcp.json` was last written on 2026-08-08 and
  is not generated by the current deployed package. It is therefore stale and
  must not be used as evidence for the current Codex launch path.
- The current `.codex/config.toml` did contain both Authorization and
  `X-AI-Net-Push = "off"`; the latter is direct evidence that native Codex MCP
  sessions using that configuration requested server push to be disabled.
