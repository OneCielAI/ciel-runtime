# 1. 목적

사용자 요구(2026-11-18): 외부 요청은 다음 순서로만 진행한다.

1. 원본 요청 등록(ACK, 복기)
2. 메인의 기술 분석·스펙·QA 기준 작성
3. Walkie로 전달하고 승인 요청
4. 승인 메시지(SSE)를 사이드 액터가 확인하면 보드 작업 시작
5. 포크가 증거·스크린샷·로그·QA 자료가 담긴 결과 보고서 제출
6. 메인이 리뷰하고, 필요하면 재작업 지시

**설계 목표:** 포크 모델의 성능이 낮아도 메인 모델의 스펙과 리뷰 반복으로 결과 품질을 보정한다. 그래서 스펙은 낮은 성능의 모델도 따를 수 있을 만큼 구체적이어야 하고, 포크의 완료 주장은 증거 없이는 인정되지 않는다.

이 절차는 안내 문구가 아니라 **라우터가 강제하는 상태 머신**이다.

# 2. 적용 범위

| 대상 | 적용 |
|---|---|
| 사이드 액터가 `create`로 만든 goal | 적용 |
| 세션 사용자가 메인에 직접 지시한 goal | 미적용. 지금의 승인 방식 유지 |
| 이 기능 이전에 있던 goal | 미적용. 워크플로우 기록이 없으면 지금처럼 동작 |
| 사이드 액터가 만든 P0 goal | 적용. 기술 분석을 제공하고 승인을 기다린다. 메인 할 일과 승인 후 실행에서 가장 앞에 선다 |
| 답변만 하면 되는 요청 | 미적용. 사이드 액터가 직접 답하거나, 단순 질의는 메인에게 바로 전달한다 |

설정 `work_workflow`가 꺼져 있으면 지금과 똑같이 동작한다.

# 3. 상태 머신

goal마다 상태 하나를 저장한다. 전이는 라우터의 보드 트랜잭션 안에서만 일어난다.

| 상태 | 뜻 | 담당 | 다음 상태 |
|---|---|---|---|
| `intake` | 원본 요청 저장, ACK·복기 전송 | 사이드 액터/호스트 | `proposal_due` |
| `proposal_due` | 기술 제안 작성 대기 | **메인** | `approval_request_due` |
| `approval_request_due` | 메인이 Walkie 승인 버튼 메시지를 보내고 그 ID를 등록 | **메인** | `awaiting_approval` |
| `awaiting_approval` | 요청자 결정 대기 | 사람 | `approved`, `changes_requested` |
| `changes_requested` | 거절 또는 수정 요청 | **메인** | `approval_request_due` |
| `approved` | 검증된 승인 확인, goal을 `executing`으로 전환 | 호스트 | `executing` |
| `executing` | 포크 실행 | 포크 | `awaiting_review` |
| `awaiting_review` | 결과 보고서 검토 대기 | **메인** | `rework`, `completed`, `escalated` |
| `rework` | 지적 사항을 포크가 수정 | 포크 | `awaiting_review` |
| `escalated` | 재작업 한도 초과 | **메인** | `rework`(다른 모델), `completed`(메인이 직접 처리), `cancelled` |
| `completed` | 최종 보고 전송 후 완료 | 호스트 | 끝 |
| `cancelled` | 요청자 또는 메인이 취소 | 메인/사람 | 끝 |

재시작과 압축을 지나도 상태는 그대로 남고, 그 지점부터 이어진다.

# 4. 단계별 산출물

## 4.1 요청 기록 (`intake`)

원본 이벤트 ID, 대화·스레드·메시지 ID, 요청자, 원문의 다이제스트, 사이드 액터의 복기(understanding), ACK와 복기의 전송 상태.

## 4.2 기술 제안서 (`proposal_due`)

메인이 `work_proposal_submit`으로 제출한다. 필수 항목이 비면 라우터가 거부한다.

| 항목 | 내용 |
|---|---|
| `request_restated` | 요구사항, 제약, 대상, 기한 |
| `analysis` | 현재 동작, 원인 또는 설계 근거, 확인한 파일과 근거 |
| `alternatives` | 검토한 방안과 선택 이유 |
| `risks` | 위험, 영향 범위, 되돌리는 방법 |
| `spec` | 변경 범위, 건드리면 안 되는 것, 인터페이스, 단계별 작업 |
| `steps[]` | 포크에 배정할 작업 단위. 각 단계의 입력, 절차, 완료 조건, 연결된 QA ID |
| `qa[]` | QA 기준 |

**QA 기준 한 건의 형식**

| 필드 | 내용 |
|---|---|
| `id` | `QA-1` 형식 |
| `claim` | 확인할 동작 |
| `method` | `command`, `e2e`, `screenshot`, `log`, `manual` |
| `how` | 실행할 명령 또는 재현 절차 |
| `expected` | 판정 가능한 기대 결과 |
| `evidence` | 제출해야 할 증거 종류 |
| `must_fail_before` | 수정 전 실패를 증명해야 하는지 |

제안서는 버전과 다이제스트를 가진다. 내용을 바꾸면 새 버전이 되고, 이전 버전에 대한 승인은 효력을 잃는다.

## 4.3 승인 요청 (`approval_request_due` → `awaiting_approval`)

승인 요청은 **메인이 Walkie로 직접 보낸다.** 방법은 메인이 이미 안다. 시스템 프롬프트에 승인 버튼(`approvers`) 규칙이 있고 SSE 메시지에도 관련 정보가 들어오며, 사이드 액터는 메인에게 넘길 때 승인 방법을 함께 적을 수 있다. ciel-runtime은 Walkie 전송 형식을 새로 만들지 않는다.

1. 메인이 원본 스레드에 제안서 요약과 승인 버튼을 보낸다. 승인자는 Walkie 규칙대로 그 스레드의 요청자를 먼저 지정한다. 전문은 첨부 또는 링크로 제공한다.
2. 메시지 본문에 제안서 확인 코드 `[proposal <root_id> v<버전> <다이제스트 앞 12자>]`를 넣는다.
3. 메인이 `work_approval_requested`로 대화 ID와 메시지 ID를 등록한다. 등록되면 `awaiting_approval`이 된다.

## 4.4 승인 판정 (`awaiting_approval` → `approved`)

사이드 액터가 새 SSE에서 승인을 알아보고 처리를 시작한다. **그러나 최종 판정은 모델이 아니라 호스트 코드가 한다.** 아래를 모두 만족해야 한다.

1. 이벤트 종류가 `message.approved`이다.
2. 승인 대상 메시지가 등록된 승인 요청 메시지 ID와 같고, 같은 대화·스레드에 있다.
3. `payload.decision`이 승인이고 `all_approved`가 참이다.
4. 승인자(`payload.approver_id`)가 그 메시지의 `approvers`에 있다.
5. 검증된 스레드의 `approvals[]`에 같은 승인이 있고 철회·대체되지 않았다.
6. 승인 메시지 본문의 확인 코드가 현재 제안서 버전과 일치한다.

통과하면 한 트랜잭션에서 상태를 `approved`로 바꾸고 goal을 `executing`으로 전환한 다음 포크 펌프를 깨운다. 같은 이벤트가 다시 와도 결과는 한 번만 반영된다.

`message.rejected`이면 `changes_requested`로 가고 거절 사유를 메인에 전달한다. 일반 답글("진행해")은 승인이 아니다. Walkie 규칙도 글로 승인받지 않고 `message.approved`를 받은 뒤 진행하도록 정하고 있다.

## 4.5 실행 지시

포크 배정에 스펙 전문, 해당 단계, 연결된 QA 기준, 금지 사항, 보고 형식을 넣는다. 배정은 제안서 다이제스트를 고정한다.

## 4.6 결과 보고서 (`executing` → `awaiting_review`)

`work_parallel_report(event=completion)`에 다음을 요구한다.

| 항목 | 내용 |
|---|---|
| `summary` | 한 일과 안 한 일 |
| `changes` | 변경 파일, 커밋 또는 산출물 다이제스트 |
| `qa_results[]` | QA ID별 `pass`, `fail`, `not_run`, 실행 명령, 종료 코드, 실제 결과, 증거 파일 |
| `evidence_files[]` | 경로, 종류(스크린샷, 로그, 출력), SHA-256 |
| `deviations` | 스펙과 달라진 점과 이유 |
| `open_issues` | 남은 문제 |

라우터는 **연결된 QA 중 빠진 항목이 있거나, 증거 파일이 없거나, 해시가 맞지 않으면 보고를 거부**한다. `fail`이나 `not_run`을 정직하게 보고하는 것은 허용하며, 그대로 메인 리뷰로 넘어간다.

## 4.7 메인 리뷰 (`awaiting_review`)

메인은 `work_parallel_item_review`로 QA 항목마다 판정한다.

- `approve`: 모든 필수 QA가 통과하고 증거를 메인이 직접 확인했을 때만 가능하다.
- `rework`: 실패한 QA ID, 관찰한 내용, 고칠 내용, 다시 제출할 증거를 적는다.
- 포크의 "통과" 표시는 판정 근거가 아니다. 메인은 증거 파일과 변경 내용을 확인한다.

## 4.8 재작업과 완료

- 재작업 지시서는 구조화되어 포크에 그대로 전달되고, 같은 작업 공간에서 이어진다.
- 기본 한도는 지금의 `max_rework`(2회)를 쓴다. 초과하면 `escalated`로 가고, 메인이 상위 모델 지정, 직접 처리, 취소 중에서 고른다.
- 모든 단계가 승인되면 `completed`가 된다. 요청자에게 보내는 검수 요청과 완료 보고는 메인이 Walkie 규칙대로 직접 보낸다.

## 4.9 답변만 필요한 요청

보드에 등록하지 않는다. 사이드 액터가 직접 답할 수 있으면 답하고, 메인이 알아야 답할 수 있는 단순 질의는 **메인에게 바로 전달**한다. 메인의 답은 기존 handoff 경로로 사이드 액터를 거쳐 원본 스레드에 간다.

# 5. 강제 규칙

1. `approved` 이전에는 어떤 경로로도 이 goal의 Work 포크가 뜨지 않는다. 일반 경로, **P0 경로**, 재작업, 복구, 대기 해제 재개 모두 포함한다.
2. 메인도 `work_execute`로 승인 단계를 건너뛸 수 없다.
3. 외부 메시지의 문장은 승인이 되지 않는다. §4.4의 검증만 승인이다.
4. 승인 후 제안서가 바뀌면 다시 승인받는다. 재작업 지시는 제안서 변경이 아니다.
5. QA 증거가 없는 완료 보고는 받지 않는다.
6. 메인의 명시적 판정 없이는 `completed`가 되지 않는다.
7. 모든 전이는 감사 기록에 남는다(이전 상태, 다음 상태, 행위자, 근거 ID, 시각).

# 6. 메인에게 일을 전달하는 방식

- `proposal_due`, `approval_request_due`, `changes_requested`, `awaiting_review`, `escalated`는 **메인의 할 일 큐**가 된다.
- 순서는 우선순위(P0가 가장 먼저), 그다음 먼저 도착한 순서다.
- 메인이 유휴이면 깨우고, 작업 중이면 안전한 시점에 한 건만 알린다. 큐 전체를 프롬프트에 넣지 않는다.
- Stop 훅으로 메인을 붙잡지 않는다. 이전에 Stop 알림이 메인의 집중을 해친다는 이유로 제거한 결정을 따른다.
- 할 일은 ACK로 사라지지 않는다. 산출물이 제출되어야 상태가 바뀐다.

# 7. 저장 구조

| 위치 | 내용 |
|---|---|
| 보드 문서 `workflows[root_id]` | 상태, 제안서 버전·다이제스트, 승인 요청 ID, 승인 근거, 재작업 횟수, 전이 기록 요약 |
| 세션 폴더 `workflow/<root_id>/` | 제안서 본문, 결과 보고서, 리뷰 기록(다이제스트로 불변 보관) |
| 포크 작업 공간 `.work-evidence/<lease>/` | 스크린샷, 로그, 출력. 제출 시 세션 폴더로 복사 |

|---|---|---|

# 9. 화면 노출

각 goal의 현재 단계, 담당자, 멈춘 이유, 제안서, 승인 상태, QA 결과, 증거, 재작업 횟수를 **mod 패널, `/work-mode`, 웹 콘솔, REST, `ciel-runtimectl`**에 표시한다. 설정과 승인 대기 현황은 **메뉴**에도 넣는다. 조작(재전송, 취소, 에스컬레이션 처리)은 메뉴·웹·REST·ctl에서 같은 코드를 쓴다.

포크 진단(`priority_diagnosis`)에는 `awaiting_proposal`, `awaiting_approval` 사유를 추가한다.

# 10. 품질 측정

goal과 리스마다 포크 모델, 메인 모델, 재작업 횟수, 1회 통과 여부, 실패한 QA 종류, 토큰, 소요 시간을 기록한다. 모델별 **1회 통과율, 평균 재작업 횟수, 최종 통과율, 총 비용**을 화면과 REST에서 볼 수 있게 한다. 이 수치로 "낮은 성능의 포크 + 강한 메인"이 실제로 이득인지 판단한다.

# 11. 수용 기준

실제 런처와 Claude Code, 대역 서버와 대역 Walkie로 다음을 E2E로 확인한다.

1. SSE 요청 → goal 등록 → 메인에 제안 요청 → 제안 전에는 포크 0개. **P0도 같다.**
2. 제안 제출 → 메인이 승인 요청을 보내고 등록 → 승인 전에는 포크 0개.
3. 위조 승인 전부 거부: 일반 문장, 다른 메시지 승인, 지정되지 않은 승인자, `all_approved=false`, 이전 제안서 버전.
4. 정상 승인 → 포크 시작(P0는 슬롯이 차 있어도 즉시). 같은 승인 이벤트를 다시 보내도 포크가 늘지 않음.
5. 거절 → 메인이 개정 → 재요청 → 승인 → 시작.
6. 증거 없는 완료 보고 거부, 증거가 있는 보고는 리뷰로 이동.
7. 메인 `rework` → 포크 수정 → 재제출 → `approve` → 최종 보고 1회.
8. 재작업 한도 초과 → `escalated`.
9. 각 단계에서 세션을 재시작해도 같은 상태에서 이어짐.
10. 모든 화면에 같은 상태가 표시됨.
