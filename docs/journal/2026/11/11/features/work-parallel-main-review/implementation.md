# Approved scope

Replace parallel reviewer forks with an explicit main-session review stage. This journal covers the packaged Claude mod host bridge, Work REST/web console, focused harness/REST/UI tests, and browser evidence. Parallel ledger/finalization implementation is owned separately ([backend journal](backend-finalization.md)).

# Host behavior

- Submitted worker results never start reviewer reservations or reviewer forks.
- The event-driven host reads the durable finalization projection already returned by `work_parallel_status` after worker reports, ledger events, session start, turn completion and Stop; there is no review polling timer.
- Idle main receives `$.prompt.submit`; busy main receives `$.session.append`.
- Main receives an allow-listed bounded receipt only: lease/item/title/path, artifact and completion digests, summary/coverage/verification, and bounded workspace metadata. Fork answers, transcripts, agent/native rows, capability tokens, repo roots, snapshot receipts and saga internals are excluded.
- Stop re-reads the board and finalization projection after the scheduler pump. Only `work_parallel_item_review` clears the decision gate.
- Every host-owned Work fork task notification is suppressed in both `session.receive` and `prompt.submit`, including delayed notifications retained by the bounded ownership tombstone.
- `/work-mode parallel` and the Observatory show `Awaiting main review`, `Rework`, `Rework (waiting for slot)` and `Finalizing` labels.

# REST and web console

- `GET /ca/work/api/v1/parallel` includes browser-safe `parallel_reviews`, `review_version`, and `reviews_truncated`; absolute repo/workspace paths and private fork/finalization fields are removed.
- `POST /ca/work/api/v1/commands/parallel-item-review` maps authenticated browser decisions to the same finalization saga with deterministic decision IDs and finalization-version CAS.
- The Parallel tab shows bounded receipt facts and Approve/Rework controls. Approve uses the confirmation dialog; Rework requires evidence text.
- The finalization sidecar is part of parallel SSE invalidation and fingerprinting, so review state changes refresh the Parallel tab.

# Follow-up changes (same day)

- Stale side-model UI removed: help text, forced-model toast, model picker and custom id, `props.model`, the `work_side_intake_model` lookup and the Observatory `M inherit` header. Side actors are labeled `native fork (main model/context)`.
- `time_limit` side handoffs keep their bounded text/due/evidence in the main prompt and Stop block, the REST side projection and the web handoff list; raw thread/SSE fields are excluded.
- The exact pending SSE fork passes the Work agent.spawn gate through `sideSpawnInput` without reading the Work ledger. `sideSpawnInput` `{deny}` is returned before Work policy, so a failed side proof is denied whether Work parallel is on or off. Side forks are unnamed and bound by exact `Side SSE <12 hex>`.
- `not_applicable` side reviews get their own bucket; main is never told to send, chase or correct a source reply for them. Pane and web delivery label: `no source reply (event referenced no message)`.
- REST preserves the backend true `workspace.changed_count` while clipping the changed-file sample to twenty rows.

# Durable review wake and roll-forward

- Review wake uses host-only `work_parallel_event(event='review_wake', operation='prepare'|'record')`; only projected wake states `pending` and `failed` are prepared, so a restart never re-wakes. A wake is notification delivery only; Stop stays gated while `decision` is null.
- `review_roll_forward` runs from the host pump for `awaiting_capacity` and decided `deciding` rows with `blocked`, at event boundaries only (worker report, turn.complete, session.start, Stop).
- Both carry `_host.internal:true`. A model-originated `review_wake` or `review_roll_forward` is denied by the mod before any router call, and the router refuses them without the marker or with any agent id.

# Rework launch protocol

- `rework_dispatch` (fork marker), then `rework_launch_intent` before `agent.spawn`; a positive spawn denial records `rework_launch_denied`; a returned native id records `rework_spawn_observed`, then normal `bind`.
- One random launch nonce per loaded mod process, carried on every intent. It is not regenerated by session.start or resetParallelHostState.
- Every launch event and the host-only `rework_launch_status` read carry `_host.internal:true`; model `_host` is replaced wholesale by `{agent_id}`, and a model-originated launch event is denied by the mod before the router.
- Each attempt has its own exact native name `work-rework-<replacement lease>-a<attempt>`.
- Reconcile reads `rework_launch_status` (exact name, `launch_ref`, observed agent id, `same_process`; the stored nonce is compared by the router, never returned).
  - Exact name listed: bind; for a person's request, `rework_launch_present` with the current `launch_ref` first (label `Rework (agent present)`).
  - Unlisted, recorded by a later or unknown process: `rework_launch_absent` with the exact name and, for spawn_observed, the exact observed agent id; then exactly one fresh dispatch.
  - Unlisted in the same process: `Rework launch stuck`, never resolved automatically.
- Person-confirmed resolution, request only, then the next pump checks the native agent list and sends `rework_launch_manual_resolve` (absent) or `rework_launch_present` (present), each with the current `launch_ref`:
  - Pane: `Resolve stuck launch…` (dashboard strip hotkey x, list view button) asks with `$.ui.ask`, then sends `rework_launch_manual_request {lease_id:<review lease>, launch_ref}` with `user_confirmed`.
  - Web: `POST /ca/work/api/v1/commands/parallel-launch-resolve {lease_id:<review lease>, launch_ref, confirmed:true, expected_finalization_version}` calls the backend helper `request_rework_launch_manual`. The controller never reads or derives the launch name. Labels: `Rework launching`, `Rework launch stuck` (display-only 30 s threshold), `Waiting for host check`, `Rework (agent present)`.
  - A stale `launch_ref` (re-dispatched, restored or bound) is refused; a retry with the same ref is idempotent.
- A fork of an already-resolved attempt that appears late is host-owned (notification suppressed), stopped once if pending/running, and never bound.
- Session start (`parallelHydrate`): an unbound main-review resume lease is reconciled through `rework_launch_status` with the same rules, never by a plain bind. Found by scenario 13 below: with a requested resolution and the fork listed, session.start called `work_parallel_status`, `work_parallel_status`, `bind`; the backend refused the bind (`rework launch intent was not observed for this agent`), the throw skipped the whole session.start pump, and the launch stayed `manual_requested`. The host read is made only when such a lease exists; worker and legacy resume leases keep the existing exact-name bind.

# Real-backend integration

`tests/test_work_mod_real_backend.py` runs the real register.js against the real `work_parallel_mcp` ledger/coordination/finalization stores and a temp git repo in a temp `CIEL_RUNTIME_CONFIG_DIR`. A restart re-imports register.js, so every in-memory mod map is lost. Thirteen scenarios:

1. approve to finalized;
2. rework intent, observed, bound, restart: one spawn, dispatch and intent;
3. spawn throws and the fork never appears: held in the same process across session.start, then resolved absent by the next process with one fresh fork and one bind, no extra resume slot, the late first-attempt fork stopped and suppressed;
4. observed but unbound fork gone after restart: resolved by exact agent id, one fresh fork;
5. web request with the fork listed late: idempotent retry, `agent present`, bound, old ref refused;
6. pane resolution: decline records nothing, confirm resolves, re-dispatch makes the old ref stale;
7. fork listed after a thrown spawn: exact reconcile after restart, no second spawn, model status never shows the name;
8. forged `_host`: launch, review_wake and roll_forward refused by the mod and the router;
9. explicit denial allows exactly one retry;
10. awaiting_capacity rolls forward at an event boundary then dispatches once;
11. idle wake prepared and recorded once across restart with Stop still gated;
12. busy wake appended and not resent after restart;
13. web request recorded, fork listed, CLI restart: session.start alone sends `rework_launch_present`, binds the listed fork, and its pump still runs.
