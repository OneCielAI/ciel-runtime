# Scope

The owned run uses a synthetic loopback Walkie SSE/MCP fixture, an owned router port and temporary config, and a real Claude Code console. No real Walkie event is sent. Product code stays frozen; each launch runs from a fresh copy whose pre-launch whole-tree digest equals `3426e4b6f17d18844e854e3c5e228ef01ea98f3ef8949bda40756c74598b9884`.

The design and prior proofs are in [the feature design](../design.md), [verification](../verification.md), and [owned probes](../probes.md).

# Harness defects — not product defects

## Wrong launch command

`run-a-20261111-073415` used `ciel_runtime.py --ca-runtime claude`; the CLI rejected `claude` as a command. The corrected launch is `ciel_runtime.py cli -- --session-id …`.

## Driver exit 130

`run-a-20261111-101537` and `run-a-20261111-102246` ended before evidence collection because the driver ran through the shell console. The cause of the console-control exit was not determined. Later runs start `python.exe` detached and attach only to the owned Claude console.

## Live profile contamination

`run-a-20261111-102831` set temporary `CIEL_RUNTIME_CONFIG_DIR` and `CLAUDE_CONFIG_DIR` but omitted `CIEL_RUNTIME_TEST_ISOLATED=1`. `runtime_paths.py` therefore wrote CLI assets to HOME:

- `~/.claude/settings.json` received 28 hook paths into `snapshot-frozen`;
- `AppData/Local/ciel-runtime/bin/ciel-runtime-statusline.py` received that package root;
- the live statusline subsequently imported from the snapshot and wrote 12 cpython-314 `.pyc` files into it.

The lead restored the live profile at 10:49:17 CST. The snapshot was restored by deleting only the 12 extra `.pyc` files, then re-verified at the recorded digest. See [pre-restore verification](snapshot/verify-before-restore2.json) and [post-restore verification](snapshot/verify-after-restore2.json).

Every later launch sets `CIEL_RUNTIME_TEST_ISOLATED=1`. The pre-launch path probe proves `CLAUDE_SETTINGS_PATH`, `CLAUDE_COMMANDS_DIR`, `CLAUDE_GATEWAY_CACHE`, `CIEL_RUNTIME_STATUSLINE_PATH`, `WORKSPACE_STATE_DIR`, and `ROUTER_INSTANCE_DIR` are all inside the owned temporary config. A live-profile guard hashes `~/.claude/settings.json`, `~/.claude/commands/*`, `AppData/Local/ciel-runtime/bin/*`, and only the owned workspace's project entry in `~/.claude.json`; it kills the owned tree on the first attributable change.

## Receipt lookup timeout

`run-a-20261111-105350` reached a processed receipt, but the driver looked for the synthetic stream cursor in `event_key`. The durable key contains the CloudEvent id instead. This caused the driver to wait until its timeout even though the product path had already completed. The harness now maps the stream marker to the CloudEvent id and parses string-valued receipt results as JSON.

# Candidate product issue — not fixed here

A temporary `CLAUDE_CONFIG_DIR` without `CIEL_RUNTIME_TEST_ISOLATED=1` still lets the runtime rewrite HOME CLI assets. That boundary may merit a separate product issue. This E2E task does not change it.

# Pre-existing engine behavior

Claude Code rewrites `ciel-work/.claude-plugin/types/claude-code-tools/index.d.ts` at plugin load. This is engine behavior, not an SSE defect. In `run-a-20261111-105350` the run-copy diff contained only that file:

- classification: `engine_written_types`;
- tool-name keys: 79 before, 78 after;
- removed key: `ClaudeDesign`;
- added keys: none;
- environment-specific `mcp__*` server tool-name keys: none.

The diff contained no fixture content and no secret. See `run-a-20261111-105350/result.json` → `run_copy_after`.

# Product defect: duplicate immediate time-limit wake

One processed `time_limit` event was submitted to main twice concurrently. Main received two identical wake blocks in one request and made one acknowledgment call against an already-stale version. The acknowledgment failed, leaving the handoff requested.

## Observations

1. `run-a-20261111-105350/gateway-request-005.json` contains the same `Ciel side event requires main action` block twice in the final main user message.
2. `run-a-20261111-105350/claude-debug.txt` records two `work_side_wake` calls starting at 16:54:35.836Z and 16:54:35.851Z, then two `$.prompt.submit` calls at 16:54:36.133Z and 16:54:36.141Z.
3. `gateway-request-005.json` responds with one `work_side_handoff` call using `expected_version: 3`.
4. `gateway-request-006.json` records the tool result: `work_side_handoff: the plan changed (stored version 4, expected 3); call work_status and retry`.
5. `run-a-20261111-105350/evidence/board-after.json` retains the handoff in state `requested`; its wake state is `queued`.
6. The source reply itself was sent once: the receipt's outbox state is `submitted`.

The frozen source contains two potential concurrent scheduling paths:

- immediate scheduling after `work_side_resolve` in `side-intake.js:805-808`;
- the `main_wakes` loop from a concurrent side claim in `side-intake.js:559-570`.

This is a correlation, not a proven root cause. The evidence proves two wake operations and two main submissions, but does not identify which caller owns each operation.

The defect violates the acceptance requirement that one time-limited event be reported immediately with its Work number and then acknowledged by main. Per the E2E stop rule, run B was not started.
